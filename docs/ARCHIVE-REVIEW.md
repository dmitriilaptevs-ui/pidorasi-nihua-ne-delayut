## 1. Что находится в архиве

- `package.json`: приложение `rubai` v0.1.0; объявлены Next.js `^15.3.0`, React `^19.0.0`, Prisma `^6.5.0`, TypeScript `^5.7.3`, Tailwind `^4.0.9`, Vitest `^3.0.7`. Это диапазоны зависимостей, а не подтверждённые версии запущенного окружения; есть `package-lock.json`.
- Next.js App Router совмещает маркетинговые страницы, login/register, dashboard, админку, внутреннее API и AI gateway. Python/FastAPI-компонента нет.
- `prisma/schema.prisma`, начальная миграция и `seed.ts`; PostgreSQL. В `compose.yaml` описаны приложение, PostgreSQL 16 и Caddy.
- `/v1/chat/completions`, `/v1/models`, `/v1/embeddings` и `/api/v1/*`-алиасы. Наличие embeddings в прототипе не расширяет утверждённый MVP автоматически.
- Адаптеры mock/OpenRouter: `src/lib/upstream/`; gateway: `src/lib/gateway.ts`.
- Mock/ЮKassa-платежи: `src/lib/payments.ts`, `src/lib/yookassa.ts`, `src/app/api/webhooks/yookassa/route.ts`.
- Четыре Vitest-файла: pricing, API-key helpers, mock provider и rate limit. Отдельный HTTP smoke script: `scripts/smoke.mjs`. Они **не запускались**.

## 2. Соответствие целевым требованиям

| Область | Что видно в коде | Разрыв с ТЗ / следующая проверка |
| --- | --- | --- |
| Стек | Next.js + TypeScript + Prisma/PostgreSQL | FastAPI отсутствует. Выбрать перенос или отдельно согласовать изменение ТЗ, см. D-02. |
| Rate limit | In-process `Map` в `src/lib/ratelimit.ts` | Нет Redis/общего лимитера для нескольких реплик. |
| API-ключи | Hash/prefix, статусы и отзыв, monthly limit; `api-keys.ts`, `api-auth.ts`, key routes | Отзыв ≤5 с и конкурентное соблюдение бюджета не доказаны тестами. |
| Email/аккаунт | Регистрация, сессии, роли и смена пароля после входа | В схеме нет верификации email/токенов сброса; отдельного восстановления пароля не обнаружено. Нет полноценной модели организаций и блокировок по ТЗ. |
| Деньги | Баланс, стоимость и `Transaction` — `BigInt` в копейках | Цены, FX, markup — `Float`; вычисления через JS `number` и округление `Math.ceil(rub * 100)`. Нет согласованного накопления точных субкопеечных сумм. |
| Финансовый журнал | Запись usage, изменение баланса и одиночная `Transaction` в DB-транзакции | Это не двойная запись со сбалансированными счетами; DB-защита неизменяемости журнала не обнаружена. |
| Резервирование | Предварительное чтение баланса/агрегата лимита, списание после генерации | Нет сущности/атомарной операции reserve. Параллельные запросы могут пройти одну и ту же проверку. Код `billing.ts` прямо допускает отрицательный баланс. |
| Повторная финализация | `Transaction.usageLogId` уникален | `UsageLog.requestId` не уникален; повторный `recordUsage` может создать другой usage record. Сквозная идемпотентность по бизнес-запросу не обеспечена этим индексом. |
| Месячные бюджеты | `keySpent` суммирует usage со статусом `ok`, месяц считается по UTC | Не учитываются активные резервы; pre-check не блокирует одновременный перерасход. Поведение перехода месяца/поздней стоимости нужно проектировать. |
| Provider cost | Pricing рассчитывает стоимость по тарифу и числу токенов | Нет полной истории фактической стоимости USD, generation ID, pricing version и дополнительных платных компонентов по ТЗ. |
| Streaming | SSE, извлечение usage, обработчик cancel, fallback оценки токенов по символам | Оценка не равна фактическим расходам. Нет durable `pending_reconciliation`; crash/disconnect и надёжность cancel в runtime не проверены. |
| Финансовая сверка upstream | Есть синхронизация каталога/курса | Не обнаружена фоновая сверка генераций/затрат OpenRouter; обновление курса не заменяет сверку расходов. |
| Пополнение | Серверная перепроверка статуса и суммы у ЮKassa; атомарное условное изменение `PENDING → SUCCEEDED`; уникальный внешний payment ID | Полезная база защиты от повторного credit. Но `createYooKassaPayment` в `src/lib/yookassa.ts` генерирует новый `Idempotence-Key: randomUUID()` при каждом вызове, а `createTopupPayment` создаёт новую внутреннюю запись: стабильной идемпотентности повторного создания нет. Currency/merchant validation, recovery и конкурентные сценарии также требуют доработки/проверок. |
| Webhook/recovery | Webhook сверяет metadata; ошибки проверки отвечают 200. Дополнительная перепроверка привязана к странице пополнения | Нет устойчивой фоновой очереди сверки; без повторного открытия страницы задержанный платёж может оставаться необработанным. |
| Фискализация | В проверенных платежных файлах нет receipt lifecycle | Не реализованы доказательства регистрации чеков предоплаты/зачёта/возврата. |
| Возвраты | Enum `REFUND` и вспомогательные изменения баланса | Не найден полный refund flow через оператора. Enum не является возвратом денег. |
| Тесты | Unit-файлы + smoke script | Не обнаружены отдельные тесты конкурентного резервирования, double-entry, платежных дублей и crash/reconciliation. Результаты существующих тестов неизвестны. |

## 3. Важные выводы для дальнейшей работы

1. Архив полезен как источник UI/UX, маршрутов и прототипа адаптеров, но **не соответствует финансовым инвариантам целевого MVP** по просмотренным участкам.
2. Не подключать реальные деньги на основании наличия `compose.yaml` или webhook route. Нужны новая модель резервов/журнала, точные расчёты, сверка и доказательства тестами.
3. Существующий подход к подтверждению платежа следует изучить и переиспользовать осмысленно, а не объявлять все платежные сценарии завершёнными.
4. Email-сценарии, фискализация, возвраты, организации, audit trail и эксплуатационные процедуры входят в отдельные задачи.
5. В прототипе есть dev defaults, demo/seed credentials и mock-платежи. До любого окружения с реальными данными требуется проверка конфигурации и изоляции; значения секретов/паролей здесь не приводятся.
6. Нужны проверка происхождения импортируемого кода, зависимостей и лицензий, а также отдельный secret scan. Настоящий обзор не утверждает, что архив не содержит секретов или уязвимостей.

## 4. Предлагаемый порядок импорта

1. Владелец и второй участник принимают D-01/D-02 из [реестра решений](DECISIONS.md).
2. Отдельным PR извлечь только проверенные исходники, сохранив историю происхождения. Не перезаписывать требования, лицензию или изменения другого участника.
3. После разрешения на разработку воспроизвести сборку и существующие тесты в изолированном mock-окружении; зафиксировать фактический результат.
4. Сопоставить реальные API/UI-контракты с целевыми, затем планировать переиспользование или перенос. Не поддерживать два источника баланса — Next.js и FastAPI.
5. Реальные интеграции разрешать только после этапа 0 и проверенного финансового контура.
