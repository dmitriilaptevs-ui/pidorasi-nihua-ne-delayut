# Реестр решений

**Статусы:** «Требование ТЗ» — задано заказчиком; «Предложение» — требует согласования; «Открыто» — решение отсутствует. «Принято локально» — согласованное ограничение текущей frontend-итерации, не production-решение. Ни один статус здесь не означает автоматически проверенную функцию.

## Уже заданные ограничения

| ID | Требование ТЗ |
| --- | --- |
| R-01 | Клиент получает ключ платформы, upstream-ключ остаётся на сервере. |
| R-02 | Предоплата в RUB, собственные тарифы и полный учёт расходов. |
| R-03 | Основные пользовательские, финансовые данные и их первичная обработка — в РФ. |
| R-04 | Резервы до платного запроса, защита от повторных списаний и конкурентных перерасходов. |

| R-06 | Замена AI-провайдера не меняет пользовательские ключи и балансы. |
| R-07 | До разработки — письменное согласование коммерческой схемы. До запуска — весь набор коммерческих, правовых и эксплуатационных условий. |
| R-08 | Нет собственных GPU, обучения, полноценного чата и сложных команд в MVP. |

## Как принимать решение

1. Открыть issue с ID, контекстом, вариантами, ограничениями и критериями выбора. Для правовых документов — только несекретные ссылки/идентификаторы.
2. Обсудить вдвоём; финансовые, юридические и security-решения согласовать с профильным ответственным.
3. Создать отдельный документ решения (ADR) и PR. Указать последствия для ТЗ, тестов, миграций и эксплуатации.
4. После одобрения обновить статус со ссылкой на ADR/PR. Исторические решения не стирать: заменять новым с явной ссылкой.

Ни схема в документации, ни закрытие GitHub issue не служат доказательством письменного разрешения поставщика или готовности к production.
