# Целевая архитектура MVP

**Статус: предложение к реализации, не описание работающей системы.** Основа — [ТЗ](SPECIFICATION.md). Начало разработки и реальные интеграции ограничены [этапом 0](STAGE-0.md). Открытые решения нельзя считать утверждёнными: [DECISIONS.md](DECISIONS.md).

В репозитории есть отдельный архив прототипа, см. [его статический обзор](ARCHIVE-REVIEW.md). Архив не распакован в рабочее дерево и не мигрирован на целевой стек. Отдельно разрешена [локальная frontend-итерация](ONBOARDING-LAB.md) в `apps/web`; её ограниченный Next.js BFF не является реализацией финансового backend, описанного ниже.

Схема ниже развивает **предложенный в ТЗ вариант FastAPI**, а не закрывает решение D-02 о переиспользовании Next.js-backend. Обязательные инварианты ТЗ (например, отзыв ≤5 с и отсутствие потерянных денег) отделены от механизмов их достижения. DB-checks, конкретные state names, outbox, правила округления и API-контракт ниже — предложения до принятия соответствующих решений D-04…D-12.

## 1. Границы системы

```text
                          Российская инфраструктура
┌────────────────────────────────────────────────────────────────────┐
│ Браузер ──TLS──> Next.js (сайт, личный кабинет)                      │
│                      │                                             │
│ SDK / агент ──TLS──> Nginx ──> FastAPI / ASGI                        │
│                               │                                    │
│  Один модульный backend:      identity / keys / models              │
│                               gateway / billing / payments / admin │
│                               │                  │                 │
│                          PostgreSQL             Redis              │
│                  источник финансовой истины   rate limits / cache  │
│                               │                                    │
│                   durable outbox → фоновые workers                 │
│                   сверка, чеки, уведомления, каталог                │
│                               │                                    │
│                       Provider Adapter                             │
└───────────────────────────────┼────────────────────────────────────┘
                                │ TLS, только согласованные данные
                                ▼
                  Разрешённый AI-провайдер / OpenRouter
```

- Backend, БД, авторизация, платёжные данные, секреты, очереди с пользовательскими данными, резервные копии и журналы с такими данными размещаются в РФ; конкретный поставщик не выбран.
- Отдельный worker — процесс того же приложения, а не преждевременное выделение независимого микросервиса. Выбор Celery или аналога открыт.
- Next.js не владеет биллингом и не получает серверный ключ AI-провайдера. Бизнес-правила и финансовые транзакции исполняет backend.
- Browser-сессия и API-ключ для SDK — разные учётные данные. Для браузера предлагаются защищённые cookies, защита от CSRF и безопасное восстановление доступа; точный механизм фиксируется отдельным решением.
- Зарубежный транспортный узел не нужен по умолчанию. Если его согласуют, он не подменяет страну клиента и не хранит основную пользовательскую БД.
- Не передавать пользовательские и финансовые данные в зарубежные error-tracking/analytics-сервисы без отдельной правовой и технической оценки.

## 2. Модули монолита

| Модуль | Ответственность | Не должен делать |
| --- | --- | --- |
| `identity` | Email, пароли, сессии, верификация, восстановление, блокировка, тип аккаунта и реквизиты | Менять баланс напрямую |
| `keys` | Выдача/хеширование/отзыв ключей, владельцы, политики доступа | Хранить или повторно показывать полный ключ |
| `catalog` | Модели, доступность, capabilities, версионные тарифы | Перезаписывать старые тарифные снимки |
| `gateway` | OpenAI-совместимый контракт, валидация, routing, streaming | Отправлять платный запрос без подтверждённого резерва |
| `providers` | Адаптеры, нормализация usage/cost, generation lookup, остаток у поставщика | Определять пользовательские балансы и наценку |
| `billing` | Резервы, бюджеты ключей, точный расчёт, проводки, сверка | Считать ошибку доказательством отсутствия затрат |
| `payments` | Создание/проверка платежей, возвраты, фискальные состояния | Доверять сумме или статусу из webhook без серверной проверки |
| `admin` | Ограниченные полномочия, корректировки через `billing` с основанием и audit, отчёты, экспорт | Напрямую редактировать проекцию баланса или удалять проводки |
| `jobs` | Outbox, повторные проверки, сверка, уведомления | Рассчитывать на однократную доставку сообщения |

Это логические границы; названия каталогов и библиотек пока не зафиксированы.

## 3. Контракты API

Планируемый внешний контракт:

- `GET /v1/models` — доступные модели в согласованном OpenAI-совместимом формате.
- `POST /v1/chat/completions` — обычный JSON-ответ и SSE при `stream: true`.
- Управляющее API для кабинета — отдельно от `/v1`, с browser-auth, ownership checks и RBAC. Маршруты и OpenAPI описать до начала параллельной frontend/backend-разработки.
- Версионировать контракт, поддерживаемые параметры, модели, tools и форматы ошибок. «OpenAI-совместимый» не означает поддержку всех OpenAI endpoints. Embeddings, images, audio и Responses API не включены в согласованный MVP автоматически.
- Поддержку tools проверить обычными и потоковыми ответами; исполнение пользовательских tools не является обязанностью платформы.
- Возвращать внутренний `request_id` для поддержки. Не раскрывать provider keys, внутренние ошибки или персональные данные.
- Ограничить размер тела, максимальный вывод, таймауты и конкурентность. Не проксировать произвольные поля, upstream URL или provider headers без allowlist.

Предложение для ошибок: 401 — неверный ключ; 403 — блокировка/запрещённая модель; 402 — недостаточно доступных средств; 429 — rate/concurrency limit; 502/503/504 — ошибки upstream. Контракт ещё необходимо утвердить и проверить стандартным OpenAI SDK. После отправки SSE-заголовков HTTP-статус не меняется; поведение при ошибке в потоке описывается отдельно.

## 4. API-ключи и лимиты

- Генерировать криптографически случайный секрет; показывать один раз по TLS. Хранить идентификатор, безопасный префикс и криптографический хеш/защищённый digest. Алгоритм и политика ротации — отдельное решение.
- В каждом запросе проверять владельца, блокировку аккаунта, статус ключа и допустимость модели. Скрытый UI-элемент не заменяет backend-авторизацию.
- Финансовые лимиты ключа учитывать в PostgreSQL **в той же транзакции**, что и резерв кошелька. Redis используется для ограничения частоты, но не является финансовым источником истины.
- Для нескольких процессов/реплик отзыв ключа и блокировка пользователя должны действовать не позднее 5 секунд. Самый простой стартовый вариант — проверка БД на каждом запросе; любое кеширование требует теста инвалидации и fail-closed поведения.
- Расход плюс активные резервы ключа не может превышать месячный бюджет. Отключение ключа не удаляет незавершённые запросы и финансовые обязательства.
- Часовой пояс месяца, политика изменения лимита, привязка позднего списания к месяцу и влияние отзыва на уже начатый stream требуют решения до реализации. Резерв хранит свой расчётный период; наступление нового месяца не освобождает старые резервы.

## 5. Путь платного запроса

### 5.1. До обращения к провайдеру

1. Проверить API-ключ, аккаунт, параметры, модель и capabilities.
2. Проверить rate/concurrency limits и доступность согласованного provider account.
3. Зафиксировать снимок тарифа, FX, наценки, разрешённых платных компонентов и выбранного upstream.
4. Рассчитать **консервативную верхнюю границу** стоимости. Учитывать вход, tools/системные сообщения, максимальный вывод, возможные reasoning tokens и дополнительные платные компоненты. Простая длина строки или средняя стоимость не гарантирует достаточного резерва.
5. Отклонить неподдерживаемую или неограничиваемую по стоимости комбинацию параметров. Не разрешать автоматический переход на более дорогой upstream сверх резерва.
6. В короткой транзакции PostgreSQL заблокировать нужные записи в едином порядке; проверить доступный остаток кошелька и бюджет ключа; создать `api_request`, резерв и запись для последующего восстановления; атомарно увеличить суммы резервов. Защитить операцию уникальным идентификатором.
7. Только после commit передать запрос провайдеру. Не удерживать DB-locks во время сетевой генерации.

### 5.2. Отправка и ответ

- До отправки сохранить намерение вызова; как можно раньше сохранить внешний generation ID и фактического провайдера.
- Разделить статусы исполнения (`queued`, `dispatching`, `streaming`, `succeeded`, `failed`, `cancelled`) и финансового расчёта (`reserved`, `pending_reconciliation`, `settled`, `released`). Ошибка исполнения не означает `released`.
- Включать учёт использования в соответствии с актуальным контрактом провайдера. Не передавать клиенту upstream-секреты и служебные финансовые метаданные.
- На stream disconnect попытаться отменить upstream, если API это поддерживает, но не считать отмену гарантией бесплатности.
- Автоматический повтор генерации после сетевой неопределённости запрещён без доказанной upstream-idempotency: иначе возможна двойная закупка инференса.

### 5.3. Финализация

- При достоверной окончательной стоимости выполнить расчёт по сохранённому тарифу, а не по текущему каталогу.
- В одной транзакции: заблокировать кошелёк и бюджет, проверить статус резерва, записать финансовую операцию и точные компоненты стоимости, обновить проекции, закрыть резерв и сохранить итоговый статус. Уникальный ключ финализации исключает повторное списание при retry.
- Если стоимость неизвестна, перевести запрос в `pending_reconciliation`, сохранить резерв и durable-задание на сверку. Нельзя освобождать деньги только потому, что истёк HTTP timeout или локальный TTL.
- При подтверждённом отсутствии затрат освободить резерв отдельной идемпотентной операцией.
- При стоимости выше резерва не расходовать чужие резервы и не скрывать расхождение. Поднять инцидент, остановить проблемный маршрут и применить заранее согласованную политику покрытия разницы. Неконтролируемый отрицательный баланс недопустим.

## 6. Биллинг и финансовые инварианты

### 6.1. Точность

- Денежные остатки, резервы, платежи и проводки в RUB — целые копейки (`BIGINT` или эквивалент).
- Закупочные цены, стоимость USD, FX, наценка и расчётные субкопеечные накопления — точные десятичные значения (`NUMERIC` / `Decimal`), не `float` / JavaScript `number`.
- Формула: `provider_cost_usd × fx_usd_rub × (1 + markup)`.
- Тариф, FX и наценку сохранять на каждый запрос, включая источник и версию. Исторические расчёты не пересчитываются при обновлении каталога.
- Субкопеечный остаток — отдельный точный расчётный показатель, не дробная проводка в копейках. Он должен учитываться при доступном остатке и бюджетах; нельзя отбрасывать дробь на каждом запросе. Конкретный способ накопления, округления и закрытия счёта нужно согласовать с бухгалтером и заказчиком.

### 6.2. Журнал

Предлагаются `ledger_transactions`, `ledger_accounts`, `ledger_entries` в дополнение к таблицам ТЗ. В одной завершённой операции сумма знаковых проводок по каждой валюте равна нулю. Выбор счетов и проводок утверждает бухгалтер.

- Записи неизменяемы после проведения; исправление — новая компенсирующая операция со ссылкой на исходную и основанием.
- Инварианты обеспечиваются не только кодом приложения: DB-ограничения, уникальные бизнес-ключи, запрет UPDATE/DELETE для прикладной роли, транзакционная проверка сбалансированности. Подробный дизайн триггеров/прав/миграций предстоит разработать.
- `wallets.balance_kopecks` — проверяемая проекция проводок, а не редактируемый источник истины. Резерв блокирует доступность, но сам по себе не означает выручку.
- Пополнение создаёт обязательство перед пользователем. Выручка возникает при оказании услуг по принятой учётной политике; пополнения нельзя суммировать в отчёте как выручку API.
- Закупка USD-кредитов у провайдера, расход инференса, комиссии, FX и налоги учитываются раздельно. Не смешивать USD и RUB в одной «балансирующей» сумме.

Обязательные инварианты после каждого commit:

1. Доступный для нового запроса остаток неотрицателен с учётом всех резервов и принятой субкопеечной политики.
2. Один reserve не может быть одновременно освобождён и списан; повторная обработка не меняет результат.
3. Расход и резервы ключа ограничены его бюджетом даже при запросах через несколько реплик.
4. Один внешний платёж/возврат не создаёт повторную проводку.
5. Проекция кошелька совпадает с финансовым журналом; расхождение — инцидент, не ручное исправление SQL.

### 6.3. Конкурентность

Кошелёк, месячный бюджет ключа и конкретный reserve изменяются транзакционно с постоянным порядком блокировок. При deadlock/serialization failure допускается ограниченный retry **только локальной транзакции**, а не повтор upstream-вызова. Lock order и isolation level необходимо зафиксировать в ADR и проверить на PostgreSQL, не только на mocks или SQLite.

## 7. Платежи, возвраты и чеки

1. Создать внутренний платёж, закрепить сумму в копейках, валюту RUB, владельца и idempotency key.
2. Создать платёж у оператора с тем же ключом; повтор после сетевой ошибки не создаёт второй платёж. Восстановление внешнего ID — отдельный сценарий сверки.
3. Webhook считать сигналом, а не доказательством оплаты. Получить платёж серверным API оператора; проверить получателя/магазин, привязку к внутреннему платежу, статус, сумму и валюту.
4. Под блокировкой платежа и кошелька атомарно отметить подтверждение, записать проводки, обновить проекцию и outbox. Уникальность привязывать как минимум к оператору, merchant account и внешнему ID.
5. Повторные и пришедшие не по порядку уведомления безопасны. Потерянные webhook восстанавливаются фоновой сверкой.
6. Статус оплаты и статус фискального документа — разные состояния. Отслеживать чеки предоплаты, зачёта и возврата по утверждённой схеме. Успешный API-ответ сам по себе не доказывает регистрацию чека.
7. Возврат — отдельный идемпотентный процесс: проверить доступный остаток, заблокировать сумму, подтвердить внешнее исполнение и провести корректные операции. Частичные возвраты, chargebacks, возврат уже использованной предоплаты и сбои фискализации требуют отдельных правил.

Никаких реквизитов карт в платформе. Demo/mock-платежи и тестовые начисления не могут быть доступны в production; одного скрытого UI-переключателя недостаточно.

## 9. Восстановление и сверка

- Outbox создаётся в одной DB-транзакции с изменением состояния. Workers работают с повторной доставкой; handlers идемпотентны, retry ограничен, зависшие задачи видны оператору.
- После crash находить незавершённые резервы и отправки. Если generation ID потерян между upstream и commit, использовать согласованные provider lookup/выгрузку и ручную очередь расследования; не выдумывать стоимость и не повторять генерацию вслепую.
- Сверять provider usage/cost, наши запросы/списания, payments/refunds/receipts и баланс кошельков с журналом.
- Неопределённые затраты имеют срок эскалации, ответственного и политику решения спора. Это не разрешение держать пользовательский резерв бесконечно — сроки и порядок освобождения при недостатке доказательств должны быть согласованы заранее.
- При недоступности финансовой БД новые платные запросы запрещены. Отказ Redis не должен отключать финансовые проверки.
- Мониторить закупочный остаток, незавершённые резервы, lag сверки/outbox, фискальные ошибки, финансовые расхождения, latency/error rate. Порог уведомления и остановки закупок задать до запуска.
- Цель «не терять подтверждённые финансовые операции» не обеспечивается одним ночным backup. Нужны согласованная модель отказов, надёжный commit, стратегия репликации/WAL/PITR, шифрование и независимые restore drills. RTO и границы RPO=0 ещё предстоит утвердить.

## 10. Безопасность и наблюдаемость

- Только TLS извне; секреты отдельно от Git, образов и frontend-bundles, с ротацией и минимальными правами.
- Не логировать Authorization, cookies, полный API-ключ, промпты/ответы и raw payment payload. Проверить middleware, proxy access logs, tracing и error-reporting, а не только собственные log statements.
- Логи: request ID, разрешённые технические метрики и статусы; доступ, срок хранения и удаление регламентированы.
- Проверять ownership каждого ресурса. Роли поддержки, финансового оператора и администратора разделить; корректировки/возвраты/смена тарифов имеют audit trail.
- Для паролей — адаптивный password hash (например, Argon2id или scrypt с согласованными параметрами), а не быстрый API-key digest. Ограничивать попытки login/register/reset, избегать раскрытия существования email, делать verification/reset токены одноразовыми с коротким сроком жизни. Ротацию/инвалидацию сессий после смены пароля и защиту от brute force проверить отдельно.
- Удаление аккаунта не означает удаление обязательных финансовых документов: политика хранения и минимизации определяется юристом.
- Доступность 99,9%, p95 overhead <200 мс и 100 конкурентных запросов — **цели ТЗ, пока не измеренные**. Методика должна отделять время gateway от инференса и учитывать длительные stream-соединения.
