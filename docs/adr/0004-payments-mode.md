# ADR-0004: Режим платежей — только YooKassa sandbox

**Статус:** принято владельцем (2026-10-05), уточняет D-13.
**Контекст:** для живых платежей нужны юридическое лицо, договор с оператором, 54-ФЗ и фискализация. Владелец выбрал sandbox-проверку.

## Решение

- В этой итерации платежи выполняются только в sandbox YooKassa; живые ключи и реальные списания не используются.
- Обязательные свойства: идемпотентность создания платежа, проверка платежа через API оператора, ровно одно зачисление на webhook (идемпотентный ключ + уникальные ограничения), отклонение дублей, поддельных подписей, неверных суммы/валюты, отдельный учёт возвратов.
- Зачисление отражается только в ledger (двойная запись), а не проекцией баланса.
- Переключение на live — отдельное решение владельца с доказательствами этапа 0; в этой итерации запрещено.

## Последствия

- Пользователи могут регистрироваться и пополнять баланс только тестовыми средствами; это не выручка.
- Код интеграции должен быть пригоден к live без переписывания: различаются только окружение и секреты.

## Реализация (2026-10-05)

- Таблица `payments` (миграция 0005) и адаптер провайдера: YooKassa API v3 (Basic shopId:secretKey, заголовок Idempotence-Key) плюс локальный `fake` для тестов и оффлайн-разработки.
- Уведомление никогда не считается доказательством: сумма и валюта берутся из запроса к API провайдера; зачисление идёт через ledger со ссылкой `payment:<provider_payment_id>`, поэтому дубликаты и повторные доставки дают ровно одно начисление; возвраты — корректировки `refund:<refund_id>`.
- Живая проверка песочницы ждёт тестовых ключей владельца (`YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`, ключ `test_…` в `apps/web/.env.local`). До этого логика покрыта тестами на локальном провайдере, а боевой endpoint отвечает `503 payments_not_configured`.
- Live-режим (ключи `live_…`) в этой итерации по-прежнему запрещён: только песочница и отдельное решение владельца.
