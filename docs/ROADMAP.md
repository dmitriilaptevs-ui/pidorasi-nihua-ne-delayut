# План реализации и приёмки

**Статус:** предлагаемый backlog, а не обещание сроков или отчёт о выполнении. GitHub issues, milestones, назначения участников и branch protection автоматически не созданы. Ничего из приёмки ниже не отмечено выполненным на основании одного чтения архива.

Источники: [ТЗ](SPECIFICATION.md), [архитектура](ARCHITECTURE.md), [этап 0](STAGE-0.md), [решения](DECISIONS.md), [обзор архива](ARCHIVE-REVIEW.md).

## 1. Зависимости и порядок

Нумерация этапов сохраняет ТЗ, но внутри работы есть зависимости:

```text
Документация + обзор имеющегося прототипа
       ↓
Этап 0: письменное согласование / решение владельца
       ↓
Решение по архиву/стеку → OpenAPI + финансовые ADR
       ↓
Этап 1: mock gateway + Этап 2: identity/ledger/reserves
       ↓
Доказанные финансовые инварианты → реальный adapter этапа 1
       ↓
Этап 3: sandbox-платежи/чеки/возвраты → согласование real payments
       ↓
Этап 4: кабинет (может идти параллельно по согласованным контрактам)
       ↓
Этап 5: системные тесты + security + restore + go/no-go
```

Нельзя подключить платный gateway без резервов, просто потому что в ТЗ он стоит раньше биллинга. До этапа 0 выполняются только согласованные документационные работы. Любой ранний mock-прототип требует явного изменения стоп-условия ТЗ.

## 2. Backlog по этапам

### Этап 0 — коммерческая и юридическая готовность

- G0-01…G0-11: [чек-лист с доказательствами и ролями](STAGE-0.md).
- P0-01: review документов вдвоём; уточнить критерии, нерешённые вопросы и приоритеты.
- P0-02: подтвердить происхождение архива; решить D-01/D-02 (что переиспользуем и какой backend).
- P0-03: согласовать назначение участников, PR workflow и владельцев интеграций.

**Выход:** разрешение на следующий этап с явными ограничениями. Отсутствие ответа не означает согласование.

### Этап 1 — gateway и provider adapter

| ID | Задача | Проверяемый результат |
| --- | --- | --- |
| G1-01 | Утвердить OpenAPI, ошибки, поддерживаемые параметры/SDK | Спецификация без реальных ключей; контракт `/v1/models` и chat completions |
| G1-02 | Изолированный mock provider и интерфейс adapters | Предсказуемые JSON/SSE/tools/usage/error/disconnect сценарии без внешних вызовов |
| G1-03 | Аутентификация gateway + rate/concurrency limits | Невалидные/отозванные ключи и запрещённые модели не достигают upstream |
| G1-04 | Связать gateway с резервами и финализацией | Нет отправки до commit резерва; неизвестная стоимость уходит на сверку |
| G1-05 | Реальный согласованный provider adapter | Актуальный контракт usage/generation, фактические cost/provider IDs, timeouts и allowlist |
| G1-06 | Долговременная сверка и закупочный остаток | Crash recovery, bounded retry, эскалация расхождений, алерты низкого остатка |

**Зависимость:** G1-04…G1-06 требуют финансовой базы этапа 2 и разрешённых интеграций. Никаких blind retries платной генерации.

### Этап 2 — пользователи, ключи и финансы

| ID | Задача | Проверяемый результат |
| --- | --- | --- |
| B2-01 | Схема PostgreSQL и миграции | Accounts/organizations, keys, wallets, journal, reserves, requests, pricing, audit/outbox |
| B2-02 | Identity и роли | Регистрация, email verification, reset password, password hashing, throttling, безопасные сессии, соглашение, блокировка, RBAC |
| B2-03 | Жизненный цикл API-ключей | Выдача один раз, hash/digest, отзыв/ротация, ownership, месячный бюджет |
| B2-04 | Двойная запись и проекции | Сбалансированные неизменяемые операции, идемпотентность, аудируемые коррекции |
| B2-05 | Резервы и лимиты | Атомарный reserve/settle/release для кошелька и ключа; lock order и race tests |
| B2-06 | Pricing и версии | Decimal/NUMERIC, FX/markup snapshot, cached/extra costs, утверждённое субкопеечное накопление |
| B2-07 | Каталог моделей | История цен, capabilities/availability, синхронизация без изменения прошлых списаний |
| B2-08 | Durable recovery и аудит | Outbox, idempotent jobs, pending reconciliation, журнал действий администраторов |

**Выход:** финансовая модель проверена на настоящем PostgreSQL, включая многопроцессную конкуренцию и повторные события.

### Этап 3 — платежи и фискализация

| ID | Задача | Проверяемый результат |
| --- | --- | --- |
| P3-01 | Создание платежей | Сохранённая сумма/валюта/владелец, стабильная идемпотентность, recovery внешнего ID |
| P3-02 | Webhook и сверка | Provider API verification, проверки merchant/currency/amount/reference, ровно одно зачисление |
| P3-03 | Фискальные документы | Предоплата/зачёт/возврат, подтверждённые статусы, retries/алерты по схеме бухгалтера |
| P3-04 | Refund lifecycle | Полные/частичные возвраты, конкуренция с API-расходом, повторные уведомления, аудит |
| P3-05 | Бухгалтерский экспорт | Предоплаты, услуги, возвраты, комиссии, FX и обязательства различимы и сверяемы |

**Выход:** sandbox-проверки плюс отдельное разрешение на real payments. Нет зачёта денег только по данным браузера или необработанному webhook.

### Этап 4 — frontend и администрирование

| ID | Задача | Проверяемый результат |
| --- | --- | --- |
| F4-01 | Регистрация/вход/профиль | Полный email/reset flow, ошибки форм, организация, подтверждение соглашения |
| F4-02 | API-ключи | Создание/одноразовый показ/отзыв/лимиты; секреты не попадают в telemetry |
| F4-03 | Каталог и подключение SDK | Понятные RUB-тарифы, capabilities, примеры с ключом платформы и её base URL |
| F4-04 | Баланс и оплата | Доступные/зарезервированные средства, корректные pending/paid/receipt статусы |
| F4-05 | Usage и расходы | Токены, стоимость, статусы и request IDs; история не меняется при новом тарифе |
| F4-06 | Админка | Пользователи/блокировка, ключи, модели/наценка, платежи/возвраты, коррекции через ledger, сверка, аналитика, экспорт |

Frontend может разрабатываться по mock-контрактам после разрешения на разработку. UI не является владельцем финансовой истины. Не добавлять полноценный AI-чат и team management в этот этап.

### Этап 5 — проверка и запуск

| ID | Задача | Проверяемый результат |
| --- | --- | --- |
| T5-01 | Финансовые property/integration tests | Инварианты, дубликаты, racing reserves, stale prices, субкопейки, бюджеты на границе месяца |
| T5-02 | Failure injection | Crash до/после отправки/commit, потеря usage/generation ID, disconnect, retry workers/webhooks |
| T5-03 | SDK и browser E2E | Стандартный OpenAI SDK, SSE/tools; браузерные user/admin journeys и ownership |
| T5-04 | Нагрузка и SLO | ≥100 concurrent, overhead p95 <200 мс в согласованном профиле, методика availability |
| T5-05 | Security и данные | Secret/dependency scans, permissions, CSRF, ключи, logging redaction, abuse controls |
| T5-06 | Backup/restore и эксплуатация | Проверочное восстановление, сверка подтверждённых операций, runbooks, алерты, ответственные |
| T5-07 | Финальный go/no-go | Закрытые коммерческие/правовые условия, критические тесты и передача доступа заказчику |

Цифры из ТЗ — цели, не результаты нагрузочного теста. Один успешный smoke test не подтверждает месячную доступность 99,9%.

## 3. Матрица приёмки MVP

Все пункты ожидают реализации/проверки. Доказательства содержат версию кода, окружение, сценарий и результат; чувствительные данные в публичный репозиторий не помещаются.

| ID | Критерий ТЗ | Минимальное доказательство | Задачи |
| --- | --- | --- | --- |
| A-01 | Регистрация и подтверждение email | Browser E2E + истёкший/повторный токен; пароль можно восстановить безопасно | B2-02, F4-01 |
| A-02 | Пополнение RUB | Подтверждённый платёж → одна финансовая операция → правильный баланс; неверная сумма/валюта отвергнуты | P3-01, P3-02, F4-04 |
| A-03 | Повторный платёж не начисляется дважды | Одновременные одинаковые webhooks, poll и retry worker оставляют один credit | P3-02, T5-01 |
| A-04 | Фискальный документ | Проверенный lifecycle предоплаты/зачёта/возврата, включая недоступность фискального сервиса | P3-03 |
| A-05 | Создание и отзыв ключа | Полный ключ показан один раз, в БД его нет; отозванный ключ отвергается на всех репликах ≤5 с | B2-03, F4-02 |
| A-06 | Работа с OpenAI SDK | Интеграционный тест поддерживаемой версии SDK с нашим base URL и ключом | G1-01, T5-03 |
| A-07 | Свой gateway и согласованный upstream | Подтверждение договора/allowlist + трассируемый request/provider/generation ID без раскрытия секретов | G0-01…03, G1-05 |
| A-08 | Потоковая генерация | Корректный SSE/tools/usage, `[DONE]`, таймауты, disconnect и ошибка после headers | G1-02, G1-04, T5-02 |
| A-09 | Списание стоимости | Точный provider cost × snapshot FX/markup, sub-kopeck policy, сбалансированные проводки | B2-04, B2-06 |
| A-10 | Конкурентное резервирование | ≥100 запросов через несколько процессов к одному кошельку/ключу; нет перерасхода, двойных списаний и потерянных резервов | B2-05, T5-01, T5-04 |
| A-11 | История использования | UI/API показывают согласованные токены, costs, статусы, неизменные исторические тарифы | F4-05, B2-07 |
| A-12 | Администратор видит финансы | RBAC E2E и сверяемые отчёты; предоплата отделена от выручки, все коррекции аудированы | F4-06, P3-05 |
| A-13 | Ошибки провайдера не теряют деньги безвозвратно | До отправки — безопасный release; после возможной генерации — сверка; поздняя стоимость не списывается дважды | G1-04, G1-06, T5-02 |
| A-14 | Сверка расходов OpenRouter | Независимые provider records сопоставлены с нашими cost/IDs; расхождения видны и имеют resolution | G1-06, B2-08 |
| A-15 | Восстановление после сбоя | Restore drill + восстановление pending operations + совпадение журнала и балансов; документированная модель отказов/RTO/RPO | T5-06 |

## 4. Дополнительные проверки функциональных требований

Помимо 15 исходных критериев, перед релизом нужно проверить функции из других разделов ТЗ. Предлагаемые сценарии ниже не подменяют исходную матрицу и требуют детализации в задачах.

| ID | Сценарий | Ожидаемое доказательство | Задачи |
| --- | --- | --- | --- |
| X-01 | Полный/частичный возврат и спорный платёж (chargeback) | Сверка внешнего результата с ledger, исключение повторной операции, конкуренция с расходом, понятная политика уже использованной предоплаты | P3-04, T5-01, T5-02 |
| X-02 | Отказ/задержка фискализации | Оплата не начисляется повторно; чек предоплаты/зачёта/возврата достигает подтверждённого статуса или попадает в контролируемый инцидент | P3-03, T5-02 |
| X-03 | Восстановление доступа и защита auth | Истёкшие/повторные токены отклонены, password hashing и throttling проверены, сессии после reset обработаны по принятой политике | B2-02, T5-03, T5-05 |

Дополнительные обязательные edge cases:

- Средства почти исчерпаны: одновременно идут API-запрос, изменение ключевого лимита и возврат.
- Тысячи маленьких запросов: нет бесплатного потребления из-за округления; дробный остаток восстанавливается после crash.
- Переход месяца и поздняя сверка старого запроса; отзыв ключа/блокировка пользователя во время stream.
- Прерывание процесса после резервирования, после отправки upstream до сохранения generation ID, после проводки до acknowledgement.
- Provider timeout/500 после возможной платной генерации; usage отсутствует, отрицательный/неполный/некорректный, цена выше зарезервированного максимума.
- Повторные и переставленные payment/refund события; фальшивый webhook, неверная metadata/currency/merchant; запрос возврата при уже потраченных средствах.
- Отказ Redis, PostgreSQL, очереди, email и фискального оператора. Обход финансовых проверок недопустим.
- Попытка доступа к чужому ключу/платежу/export; логирование секретов через upstream errors и tracing.
