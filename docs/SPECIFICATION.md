## Цель проекта

Создать российский сервис, аналогичный Caila (<https://caila.io/>), который позволяет физическим лицам и компаниям оплачивать использование зарубежных AI-моделей в рублях и получать доступ к ним через единый API.

Основная бизнес-модель — перепродажа доступа к AI-инференсу с собственной наценкой на стоимость запросов к OpenRouter.

Ключевой принцип архитектуры: пользователь получает API-ключ платформы, а не ключ OpenRouter. Все запросы проходят через сервер платформы, где выполняются аутентификация, маршрутизация, учёт расхода токенов, тарификация и списание средств с пользовательского баланса.

## 1. Анализ референса Caila и принципиальные ограничения

В качестве функционального референса берём следующие возможности:

| Возможность | Этап |
| --- | --- |
| Регистрация пользователей | MVP |
| Пополнение баланса в рублях | MVP |
| Личный кабинет | MVP |
| Каталог доступных AI-моделей | MVP |
| Единый OpenAI-совместимый API | MVP |
| Создание и отзыв API-ключей | MVP |
| Лимиты расхода по ключам | MVP |
| Статистика токенов и стоимости | MVP |
| Работа с AI-агентами и SDK | MVP |
| Управление командами | Второй этап |
| Встроенный AI-чат | Второй этап |
| Собственный хостинг AI-моделей | Отдельный этап |

**Критическое условие запуска: необходимо согласовать коммерческую перепродажу с OpenRouter.**

В предоставленном ТЗ указано, что в опубликованном Enterprise Access Agreement от 22 июня 2026 года, пункт 2.3.7, содержится ограничение на перепродажу и предоставление третьим лицам доступа к сервису. Поэтому нельзя считать, что обычный или Enterprise-аккаунт автоматически разрешает создание независимого API-реселлера.

До начала разработки необходимо получить письменное подтверждение допустимости бизнес-модели, возможности обслуживания российских клиентов, порядка оплаты и применимых ограничений на модели.

Архитектуру проектируем с возможностью замены OpenRouter на другого провайдера, не затрагивая пользователей и их балансы.

## 2. Архитектура веб-приложения

Предлагается архитектура из двух основных частей: российская инфраструктура для пользователей, платежей и бухгалтерского учёта и отдельный модуль подключения к зарубежным AI-провайдерам.

```text
Пользователь (сайт / API / AI-агент)
    ↓
Web + API Gateway (авторизация / лимиты / защита)
    ↓
Backend — Россия:
    • API-ключи;
    • баланс и биллинг;
    • база данных;
    • каталог моделей.
    ↓
AI Provider Gateway (выбор провайдера / учёт запросов)
    ↓
OpenRouter API
    ↓
Провайдер AI-модели (инференс и генерация ответа)
```

### 2.1. Где размещать серверы

В рамках MVP предлагается использовать облачную инфраструктуру российского провайдера: Selectel, Yandex Cloud либо другого подходящего поставщика. Конкретного поставщика выбрать после сравнения стоимости и необходимых условий по защите данных.

| Компонент | Местоположение |
| --- | --- |
| Сайт и личный кабинет | Россия |
| Авторизация пользователей | Россия |
| Основная база данных | Россия |
| База платежей | Россия |
| Хранение пользовательских ключей | Россия |
| API Gateway | Россия |
| Биллинг | Россия |
| Зарубежный транспортный узел, если нужен | За рубежом |
| Инференс AI-моделей | Инфраструктура разрешённых зарубежных провайдеров |

Дополнительный зарубежный узел не должен хранить основную пользовательскую базу или использоваться для сокрытия страны клиента от поставщика. Его необходимость зависит от согласованной с провайдером схемы подключения и реальной сетевой доступности.

На начальном этапе собственные GPU не нужны: вычисления осуществляют сторонние провайдеры.

### 2.2. Предлагаемый технологический стек

- Frontend: Next.js + TypeScript.
- Backend: Python + FastAPI.
- API Gateway: FastAPI / ASGI, Nginx.
- Database: PostgreSQL.
- Cache, rate limits: Redis.
- Очередь фоновых заданий: Celery или аналог.
- Контейнеризация: Docker.
- CI/CD: GitHub Actions или GitLab CI.
- Мониторинг: Prometheus + Grafana.
- Логи ошибок: Sentry или аналог.
- Платёжная интеграция: ЮKassa / Т-Банк.
- Управление секретами: KMS / Vault.

Начать с модульного монолита, а не с большого количества микросервисов. Логически разделённые модули должны позднее выноситься в независимые сервисы без переписывания бизнес-логики.

## 3. Основные функциональные модули

### 3.1. Регистрация и авторизация

Пользователь должен иметь возможность зарегистрироваться по электронной почте, подтвердить адрес, восстановить пароль, просмотреть профиль и историю платежей.

Обязательные функции:

- Регистрация и вход.
- Подтверждение email.
- Восстановление пароля.
- Принятие пользовательского соглашения.
- Разграничение обычного пользователя и администратора.
- Блокировка аккаунта при подозрительной активности.

Для корпоративных клиентов предусмотреть отдельный тип аккаунта с реквизитами юридического лица.

### 3.2. API-ключи

Каждый пользователь должен иметь возможность создавать собственные ключи для подключения сторонних приложений.

Пример формата ключа: `sk-platform-****************`.

Пользователь может создать несколько ключей, например:

- Key 1 — Cursor — лимит 3 000 ₽/мес.
- Key 2 — собственный агент — лимит 5 000 ₽/мес.
- Key 3 — тестирование — лимит 500 ₽/мес.

Для каждого ключа хранить ID владельца, имя, дату создания, статус, ограничения и историю использования.

Полный ключ показывается только при создании. В базе хранится его криптографический хеш и безопасный идентификационный префикс. Должна существовать возможность немедленно отозвать или перевыпустить ключ.

### 3.3. Каталог моделей

Создать страницу с доступными AI-моделями. Информация по каждой модели:

- Название и поставщик.
- Размер контекстного окна.
- Цена входных токенов.
- Цена выходных токенов.
- Цена кэшированных токенов, если применимо.
- Поддержка tools/function calling.
- Поддержка streaming.
- Доступность.

Цены первоначально загружаются из OpenRouter и преобразуются в рубли с учётом наценки. Каталог должен обновляться автоматически, но изменения закупочных цен и коэффициентов не должны задним числом изменять историю списаний.

## 4. Главный модуль: маршрутизация запросов на OpenRouter

Сервис должен предоставлять собственный endpoint:

```text
https://api.example.ru/v1/chat/completions
```

Это пример адреса, не действующий домен проекта. Пользователь подключается через стандартные OpenAI-совместимые библиотеки, используя URL платформы и собственный API-ключ.

### 4.1. Последовательность обработки запроса

1. Получение запроса. Пользователь отправляет запрос к выбранной модели с использованием выданного API-ключа.
2. Аутентификация. Backend определяет ключ, владельца и состояние аккаунта.
3. Проверка баланса. Система проверяет доступные средства, ограничения ключа и допустимость выбранной модели.
4. Резервирование стоимости. На балансе временно блокируется сумма для оплаты запроса с учётом максимального допустимого расхода.
5. Маршрутизация. Запрос направляется на OpenRouter с использованием серверного ключа, согласованного для данного бизнес-сценария.
6. Получение результата. Ответ возвращается пользователю, в том числе в потоковом режиме.
7. Расчёт стоимости. Система получает фактические данные потребления и рассчитывает цену в рублях.
8. Списание и сохранение. Средства списываются, резерв освобождается, а операция записывается в финансовый журнал.

ТЗ ссылается на получение данных использования в ответе OpenRouter через `usage: {"include": true}`, а также отдельное получение сведений о генерации через `/api/v1/generation`. Формат и актуальность контракта проверить перед реализацией адаптера.

### 4.2. Требования к учёту запросов

Для каждого вызова API фиксировать:

- Request ID — внутренний идентификатор.
- User ID — владелец аккаунта.
- Key ID — использованный ключ.
- Model — название модели.
- Provider — фактический поставщик.
- Input tokens — входные токены.
- Output tokens — выходные токены.
- Cached tokens — кэшированные токены.
- Cost USD — стоимость у провайдера.
- Cost RUB — стоимость для клиента.
- FX rate — использованный курс.
- Markup — наценка.
- Status — успешно / ошибка / отменено.
- Timestamp — дата и время.

Дополнительно хранить внешний идентификатор генерации OpenRouter, версию тарифа и сведения о дополнительных платных компонентах запроса.

### 4.3. Обработка ошибок

Предусмотреть ситуации:

- Недостаточно денег на балансе.
- Неверный или отозванный API-ключ.
- Модель недоступна.
- Провайдер вернул ошибку.
- Превышен rate limit.
- Клиент прервал streaming.
- Ответ был сгенерирован частично.
- OpenRouter списал средства, но локальная система не получила окончательную стоимость.

**При ошибке нельзя автоматически считать запрос бесплатным.** Требуется выяснять, была ли фактическая генерация и возникли ли затраты.

## 5. Платёжная система и учёт баланса

Для MVP предлагается предварительная оплата. Пользователь пополняет внутренний баланс в рублях, после чего расходы на AI-инференс списываются по мере использования.

Сценарий пополнения:

1. Пользователь выбирает сумму пополнения.
2. Backend создаёт платёж с уникальным идентификатором.
3. Пользователь оплачивает банковской картой или другим подключённым способом.
4. Платёжный провайдер сообщает серверу об успешной оплате.
5. Backend проверяет платёж непосредственно через API платёжного провайдера.
6. Система начисляет средства на внутренний баланс и фиксирует операцию.

В качестве первоначальной интеграции можно использовать ЮKassa (<https://yookassa.ru/>). ТЗ ссылается на webhook `payment.succeeded`, проверку статуса платежа и варианты фискализации по 54-ФЗ.

Повторная доставка webhook не должна повторно пополнять баланс. Применять idempotency key и уникальные ограничения на идентификаторы внешних платежей.

## 6. База данных

Для MVP достаточно PostgreSQL. Финансовый учёт должен проектироваться значительно строже, чем обычная база сайта.

Основные таблицы:

| Таблица | Назначение |
| --- | --- |
| `users` | Пользователи |
| `organizations` | Организации и реквизиты |
| `api_keys` | Выданные ключи и владельцы |
| `wallets` | Пользовательские балансы |
| `ledger_entries` | Финансовые операции |
| `payments` | Платежи и статусы |
| `refunds` | Возвраты |
| `api_requests` | История запросов |
| `models` | Каталог моделей |
| `model_pricing` | Версии тарифов |
| `provider_accounts` | Подключения к провайдерам |
| `provider_reconciliation` | Сверка расходов |
| `audit_logs` | Действия администраторов |

### 6.1. Пример структуры пользователя

```json
{
  "user_id": "usr_1001",
  "email": "user@example.com",
  "account_type": "individual",
  "created_at": "2026-09-26T12:00:00Z",
  "status": "active"
}
```

### 6.2. Пример записи о балансе

```json
{
  "wallet_id": "wal_1001",
  "user_id": "usr_1001",
  "currency": "RUB",
  "balance_kopecks": 150000,
  "reserved_kopecks": 0
}
```

Все суммы в рублях хранить в целых копейках. Валютные расчёты и тарифы хранить в точных десятичных типах, не используя двоичную арифметику с плавающей точкой для денежных сумм.

### 6.3. Финансовая история

Необходимо иметь возможность восстановить происхождение и расходование каждого рубля. Рекомендуется использовать неизменяемый журнал проводок по принципу двойной записи.

Пример операций:

- Пополнение: +1 000 ₽.
- Расход на модель A: −12 ₽.
- Расход на модель B: −5 ₽.
- Корректировка стоимости: +2 ₽.
- Возврат клиенту: −100 ₽.

Итоговый баланс не должен определяться вручную редактируемым числом без подтверждения финансовым журналом.

Критерий: одновременно могут выполняться десятки запросов с одного пользовательского ключа, но они не должны приводить к двойному списанию, потерянным проводкам или неконтролируемому отрицательному балансу. Потребуются транзакции БД, атомарное резервирование средств и механизм сверки.

## 7. Тарификация и экономика проекта

Разработать отдельный модуль расчёта стоимости:

```text
P_client = C_provider × R_USD/RUB × (1 + M)
```

- `C_provider` — фактическая стоимость запроса в долларах.
- `R_USD/RUB` — установленный коммерческий курс.
- `M` — коэффициент наценки.

При наценке 30% множитель составляет 1,30.

Сервис должен поддерживать отдельные наценки по моделям, категориям пользователей и контрактам.

Наценка 30% не означает прибыль 30%. Из выручки необходимо финансировать закупку инференса, комиссии платёжных систем, международные расчёты, налоги, инфраструктуру и поддержку.

Для небольших запросов требуется накапливать точную стоимость в высокоточной форме и округлять денежные списания по согласованному алгоритму. Это исключит бесплатное потребление вследствие постоянного округления стоимости до нуля.

### 7.1. Финансовая аналитика

В административной панели отображать:

- Revenue RUB — оплаченный пользователями объём услуг.
- Provider cost USD — расходы на OpenRouter.
- Provider cost RUB — расходы в рублёвом эквиваленте.
- Gross profit — выручка от использования минус прямые расходы.
- Payment fees — комиссии эквайринга.
- FX expenses — расходы на международные расчёты.
- Taxes — налоговые обязательства.
- User liabilities — неиспользованные предоплаты пользователей.

Разделить полученные предоплаты, выручку за фактически использованный API и налогооблагаемые поступления. Эти показатели могут отличаться по датам и правилам признания.

## 8. Юридическая организация бизнеса в России

Самостоятельная задача для юриста и бухгалтера, которую необходимо выполнить до публичного запуска.

Предлагаемая конструкция: российское ООО продаёт услуги по предоставлению доступа к AI-инференсу через собственную программную платформу.

Подготовить договорную модель, в которой компания выступает поставщиком услуги, а не платёжным кошельком или неформальным посредником по покупке зарубежных API-ключей.

### 8.1. Организация российской компании

- Регистрация ООО.
- Выбор подходящих кодов ОКВЭД.
- Открытие расчётного счёта.
- Выбор системы налогообложения.
- Подключение интернет-эквайринга.
- Подключение фискализации.
- Организация бухгалтерского и налогового учёта.
- Разработка публичной оферты и правил использования.

Коды ОКВЭД и формулировку предмета договора определяет юрист с учётом фактического способа предоставления услуги.

### 8.2. Налогообложение

В исходном ТЗ для финансовой модели предложены два варианта УСН:

- УСН «Доходы» — базовая ставка 6%.
- УСН «Доходы минус расходы» — базовая ставка 15%.

ТЗ относит эти базовые ставки к 2026 году. Применимые региональные ставки и право на УСН проверить для конкретного ООО.

Для перепродажи отдельно исследовать УСН «Доходы минус расходы», поскольку закупка инференса может составлять существенную долю поступлений.

Возможность учёта зарубежных затрат должна подтверждаться договором, платёжными и первичными документами и соответствовать требованиям НК РФ.

**Утверждения исходного ТЗ о НДС в 2026 году, требующие проверки:**

- По указанным в ТЗ опубликованным правилам ФНС налогоплательщики УСН с доходом за 2025 год не более 20 млн рублей в общем случае освобождаются от НДС с начала 2026 года.
- При превышении порога в течение 2026 года обязанности по НДС возникают с первого числа следующего месяца.
- Предусмотрены общая ставка 22% и специальные ставки 5% или 7% при выполнении соответствующих условий.

Учитывать налоговый режим при формировании цены, чтобы его изменение не сделало перепродажу убыточной.

Проверить порядок НДС при приобретении электронных услуг у иностранной организации. В зависимости от структуры договора и статуса контрагента у российского покупателя могут возникать обязанности налогового агента. ТЗ ссылается на разъяснения ФНС по применению статьи 174.2 НК РФ к таким операциям.

### 8.3. Фискализация платежей

Пополнение баланса предполагается оформлять как предоплату за будущие услуги.

Реализовать формирование чеков и их учёт по 54-ФЗ. Бухгалтер определяет корректные признаки предмета и способа расчёта, а также порядок зачёта предоплаты при оказании услуг.

ТЗ ссылается на документацию ЮKassa о чеках при получении платежа и зачёте предоплаты.

## 9. Оплата зарубежного OpenRouter

Разделить два денежных потока.

**Входящий:** российский пользователь → оплата в рублях → российское ООО → расчётный счёт в России.

**Исходящий:** российское ООО → разрешённый международный расчёт → OpenRouter → оплаченный лимит использования API.

### 9.1. Предпочтительный сценарий

Прямые расчёты между российским ООО и OpenRouter при согласии сторон и банка.

Выяснить у OpenRouter:

1. Возможно ли заключить договор с российским юридическим лицом?
2. Допустима ли перепродажа API в составе собственной платформы?
3. Возможна ли оплата по инвойсам?
4. Какие способы оплаты доступны для такого контрагента?
5. Какие документы предоставляются для бухгалтерского и налогового учёта?
6. Допустимо ли обслуживание конечных пользователей из РФ?
7. Какие ограничения действуют на конкретные модели и поставщиков?

ТЗ указывает, что кредитная система OpenRouter номинирована в USD, а в справке перечислены банковские карты, AliPay и USDC; для других вариантов предлагается обращаться в поддержку. Наличие способа оплаты само по себе не подтверждает возможность его законного использования конкретным российским ООО.

### 9.2. Альтернативный сценарий

Если прямой договор невозможен, юристу рассмотреть реально действующую иностранную компанию или независимого поставщика, который вправе продавать услуги российскому ООО.

Такая структура должна иметь действительные договоры, экономическое содержание операций, правомерный способ расчётов и надлежащее налоговое оформление.

Недопустимы фиктивная иностранная компания, номинальные аккаунты или сокрытие фактического получателя услуг.

ТЗ ссылается на разъяснение Банка России от 16 января 2026 года: российские специальные экономические меры не устанавливают общего запрета на оплату внешнеторговых договоров оказания услуг с нерезидентами, не относящимися к определённым подсанкционным лицам. Конкретный платёж всё равно зависит от контрагента, банка, применимых ограничений и законодательства других юрисдикций. Содержание и применимость разъяснения необходимо проверить.

**Коммерческий запуск зависит от документально подтверждённой, устойчивой и законной схемы закупки AI-инференса.**

## 10. Персональные данные и безопасность

Регистрацию, профили, платёжные записи и ключи проектировать с первичной обработкой и хранением соответствующих персональных данных на территории РФ.

Обеспечить соответствие применимым требованиям 152-ФЗ, включая уведомление Роскомнадзора, меры защиты, порядок удаления данных и оценку трансграничной передачи.

Отдельно исследовать данные, передаваемые зарубежному AI-провайдеру. Промпты могут содержать персональные данные; их нельзя автоматически считать обезличенными.

Требования к реализации:

- TLS на всех внешних соединениях.
- Не хранить полные пользовательские API-ключи.
- Не записывать полные промпты и ответы в обычные технические логи.
- Шифровать резервные копии и секреты.
- Разграничить доступ администраторов к пользовательской и финансовой информации.
- Автоматическое резервное копирование.
- Защита от злоупотреблений API.
- Журнал административных действий.

В оферте объяснить передачу запросов зарубежным провайдерам для обработки и описать применимые ограничения на использование данных.

## 11. Административная панель

Администратор должен управлять сервисом без вмешательства разработчиков.

Функции:

- Пользователи: поиск, блокировка, просмотр аккаунта.
- Балансы: просмотр, корректировка через финансовые операции.
- Платежи: поиск, статусы, возвраты.
- API-ключи: просмотр владельца, отзыв, ограничения.
- Модели: включение и отключение.
- Наценка: изменение тарифов.
- Расходы OpenRouter: сверка с внутренней системой.
- Финансовая аналитика: выручка, расходы, прибыль.
- Технические логи: ошибки, задержки, недоступность моделей.

Экспорт платёжных операций и оказанных услуг для бухгалтера.

## 12. Дополнительные требования к надёжности

Целевые показатели MVP для собственной инфраструктуры, не гарантии OpenRouter или поставщиков моделей:

| Показатель | Цель |
| --- | --- |
| Доступность собственного API | 99,9% в месяц |
| Дополнительная задержка API Gateway | p95 менее 200 мс в нормальных условиях, без времени инференса |
| Одновременные запросы | Не менее 100 на первом этапе |
| Время отзыва API-ключа | Не более 5 секунд |
| Потеря подтверждённых финансовых операций | Не допускается |
| Восстановление после сбоя | Документированная процедура |
| Резервное копирование | Автоматическое, с проверкой восстановления |

Мониторинг остатка средств на OpenRouter и уведомления при достижении минимального уровня.

Не допускать ситуации, когда пользователи имеют положительный рублёвый баланс, но компания не может оплачивать их запросы у зарубежного поставщика.

## 13. Этапы реализации

### Этап 0. Коммерческая и юридическая подготовка

Согласовать с OpenRouter допустимость бизнес-модели, определить юридическое лицо, платёжного оператора, налогообложение и способ международных расчётов.

### Этап 1. Разработка API Gateway

Собственный API, авторизация по ключам, подключение OpenRouter, streaming и сбор статистики использования.

### Этап 2. Пользователи и биллинг

Регистрация, база данных, генерация ключей, балансы, резервирование, списание и финансовый журнал.

### Этап 3. Платёжная интеграция

Оплата в рублях, webhook, фискализация, возвраты и бухгалтерский экспорт.

### Этап 4. Frontend и личный кабинет

Сайт, каталог моделей, страница пополнения, статистика расходов, управление ключами и документация API.

### Этап 5. Тестирование и запуск

Одновременные запросы, списания, ошибки провайдеров, доступность, безопасность и финансовая сверка.

## 14. Критерии приёмки проекта

MVP завершён после успешного выполнения проверок:

- [ ] Пользователь может зарегистрироваться и подтвердить email.
- [ ] Пользователь может пополнить баланс в рублях.
- [ ] Успешный платёж фиксируется только один раз.
- [ ] Для платежа формируется необходимый фискальный документ.
- [ ] Пользователь может самостоятельно создать и отозвать API-ключ.
- [ ] Ключ работает со стандартным OpenAI-совместимым SDK.
- [ ] Запрос проходит через собственный Gateway и согласованного провайдера.
- [ ] Сервис поддерживает потоковую генерацию ответа.
- [ ] Стоимость запроса списывается с баланса пользователя.
- [ ] Несколько одновременных запросов корректно резервируют средства.
- [ ] Пользователь видит историю использования и расходов.
- [ ] Администратор видит выручку, расходы и состояние платежей.
- [ ] Отказ провайдера не приводит к безвозвратной потере средств пользователя.
- [ ] Система выполняет сверку с фактическими расходами OpenRouter.
- [ ] Платформа восстанавливается после проверочного сбоя.

## Итоговая постановка задачи

Создать независимую российскую AI API Platform, позволяющую физическим и юридическим лицам покупать доступ к AI-моделям за рубли.

Платформа предоставляет собственные API-ключи и OpenAI-совместимый интерфейс, маршрутизирует запросы через коммерчески согласованные подключения к OpenRouter и другим поставщикам, учитывает фактическое потребление, автоматически рассчитывает стоимость услуг с наценкой и списывает средства с баланса.

Российская инфраструктура обеспечивает регистрацию, оплату, защиту данных, финансовый и налоговый учёт.

Основная коммерческая функция — доход от разницы между стоимостью услуг для клиентов и полной себестоимостью закупленного AI-инференса.

**Границы MVP:** без собственных GPU, обучения моделей, полноценного AI-чата и сложной корпоративной системы управления командами. Приоритет — надёжный API-шлюз, корректный биллинг и легальная работа с рублёвыми платежами и зарубежными поставщиками.
