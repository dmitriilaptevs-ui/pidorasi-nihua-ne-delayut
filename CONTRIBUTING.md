# Совместная работа над проектом

## 1. Текущий объём работ

Разрешена ограниченная локальная frontend-итерация: [ONBOARDING-LAB.md](docs/ONBOARDING-LAB.md). Код находится в `apps/web`; [инструкция запуска](apps/web/README.md). Владелец сообщил о согласовании OpenRouter, но credentials отложены и real OAuth/инференс ещё не проверены. Остальные условия [этапа 0](docs/STAGE-0.md) сохраняются. Архив `rubai-main.zip` оставлен без изменений; не запускайте его с реальными ключами/деньгами и не считайте готовым MVP.

Каждый разработчик использует **свой GitHub-аккаунт, свою авторизацию устройства и свой локальный клон**. Не передавайте OAuth-токены, пароли, 2FA-коды или одну общую SSH-идентичность.

Если другу ещё нужен доступ, владелец приглашает его через **Settings → Collaborators** по его GitHub username. Наличие ссылки на публичный репозиторий даёт чтение, но не push. Эта инструкция сама по себе никому доступ не выдаёт.

## 2. Первый запуск рабочего места

```bash
# Если GitHub CLI ещё не авторизован на вашем устройстве:
gh auth login --hostname github.com --git-protocol https --web
gh auth setup-git --hostname github.com
gh auth status

# Если локальной копии ещё нет:
gh repo clone dmitriilaptevs-ui/pidorasi-nihua-ne-delayut
cd pidorasi-nihua-ne-delayut
```

Настройте **свои** `git config --local user.name` и `user.email`. Для приватности возьмите точный noreply-email в GitHub **Settings → Emails**; не копируйте чужую подпись коммитов.

Для локальной frontend-итерации см. [apps/web/README.md](apps/web/README.md). Docker Compose, production-инфраструктура и финальный backend пока не определены. Никакой сервис автоматически не разворачивается.

## 3. Ветки и Pull Request

Перед работой убедитесь, что локальные изменения сохранены. Не используйте `reset --hard` или force-push для «синхронизации» с другом.

```bash
git switch main
git pull --ff-only origin main
git switch -c docs/phase-zero-checklist

# Внесите изменения. Проверьте именно то, что попадёт в коммит:
git status --short
git diff
git add docs/STAGE-0.md
git diff --cached --check
git diff --cached

git commit -m "docs: уточнить условия этапа 0"
git push -u origin docs/phase-zero-checklist
gh pr create --base main --fill
```

- Одна небольшая законченная задача — одна ветка/PR; `docs/*`, `feat/*`, `fix/*`, `chore/*`.
- Перед началом договориться о владельце задачи и затрагиваемых файлах. API-контракт и финансовая схема меняются согласованно, не двумя независимыми реализациями.
- Второй участник делает review. Нельзя обходить финансовые/security-проверки ради «быстрее заработало».
- Не работать вдвоём в одном worktree; для параллельной работы использовать отдельные клоны/ветки.
- Не переписывать общую ветку. Для обновления своей опубликованной ветки можно выполнить `git fetch origin` и `git merge origin/main`, затем разрешить конфликты и повторить проверки.
- `main` предназначена для проверенных изменений. Squash merge — предложение команды, не уже включённая настройка GitHub.

### Рекомендуемые правила защиты `main`

Владелец может включить PR перед merge, одно независимое approval, разрешение всех обсуждений и запрет force-push. После появления настоящего CI — добавить реально существующие required checks. Доступность rulesets зависит от настроек/тарифа GitHub.

**Настройки защиты веток в этой работе не изменялись.** CI workflows и обязательные проверки не создавались. Не считать текст в README технической защитой.

## 4. Разделение работы на двоих

Предложение, а не назначение конкретных людей:

| Направление A | Направление B | Совместно |
| --- | --- | --- |
| Backend, миграции, ledger, gateway, provider adapter, reconciliation | UX, кабинет, каталог, формы ключей/платежей, SDK-примеры и документация | OpenAPI, безопасность, платежи/чеки, нагрузочные и финансовые тесты, review |

Пока этап 0 полностью не закрыт, работа ограничивается требованиями/контрактами/анализом и отдельно разрешённой локальной frontend-итерацией. Внешние согласования принадлежат владельцу и профильным специалистам, а не автоматически разработчикам.

## 5. Безопасность публичного репозитория

- Не коммитить `.env`, реальные ключи, cookies, дампы БД, backups, логи с персональными данными, договоры, банковские реквизиты и документы клиентов.
- Только placeholders в `.env.example`. `.gitignore` не удаляет уже закоммиченные данные и не проверяет содержимое ZIP.
- Перед импортом архива проверить происхождение, лицензии, секреты и dev defaults. Не публиковать вложенные `.git`, окружения, дампы и build output.
- При утечке сначала отозвать/перевыпустить секрет; удаление файла не убирает его из истории Git. Очистку общей истории согласовать отдельно.
- В issues/PR публиковать только обезличенные request ID и безопасные технические данные. Секретные детали инцидента передавать владельцу приватно.
- Не добавлять реальные provider calls или платёжные операции в тесты по умолчанию. Любой платный или production-тест требует отдельного согласования.

## 6. Готовность PR

- Связанная задача, объём изменений и ограничения описаны.
- Статус «предложено» не подменён статусом «реализовано/проверено».
- Для документации: проверены локальные ссылки, примеры, `git diff --check`.
- Для будущего кода: тесты normal/error/concurrent/retry/crash paths, миграции и безопасность; недоступные проверки перечислены честно.
- Финансовые изменения имеют проверки инвариантов на PostgreSQL. UI smoke-тест не доказывает корректность денег.
- Новые допущения зафиксированы в [реестре решений](docs/DECISIONS.md); изменения ТЗ явно согласованы.
- Второй участник выполнил review; риски запуска и незавершённые проверки не скрыты.
